# Пилотная кампания AR-12

Каталог кампании — `case/campaign/ar-12-pilot`. Цель — оценить среднее время подготовки и проверки кандидата и расход токенов исследователя перед основной кампанией.

## Условия

- Исследовательская модель — DeepSeek V4.1 Flash. Оператор до запуска фиксирует идентификатор модели на внутреннем endpoint, харнес, режим рассуждения и возможность получить счётчики usage по каждому вызову. Решатели и оценщик работают без LLM.
- Данные — текущий AR-12 train из 14 281 строки. В [evaluation-ids.txt](evaluation-ids.txt) зафиксирована общая проверочная подвыборка из 256 сообщений, по 128 на каждый класс. Она выбрана с seed 42 отдельно по классам из списков, отсортированных по `id`. Остальные 14 025 сообщений используются для обучения и настройки, включая переобучение трёх стартовых кандидатов. Public и private в пилоте пусты.
- Метрика пилота — `ar12-tpr-v3`, направление `maximize`. Балл равен TPR при FPR ≤ 5%, иначе 0. p99 и throughput можно записать диагностически на прогретом фильтре. Для основной кампании с ресурсными гейтами нужен отдельный доверенный замер. На 128 безопасных сообщениях один ложный блок меняет FPR примерно на 0,78 процентного пункта.
- Исследователи могут менять признаки, модель, параметры и порог, используя обучающую часть train и файлы кандидата. Режим оценки, подвыборка, лимит и модель исследователя фиксируются до поиска.
- Выполнение последовательное, один кандидат за раз. Таймаут проверки кандидата определить по первому сквозному прогону при подготовке. MLflow для пилота не требуется. Источник результатов — журнал Arena и учёт usage исследовательского харнеса.

## Бюджет и завершение

Черновой лимит — 6 предложений. Три стартовых кандидата `matching`, `boosting` и `transformer` и по одному новому варианту от каждого с ID `variant-matching`, `variant-boosting`, `variant-transformer`. Стартовые кандидаты дают опорные замеры оценки. Новые варианты дают три наблюдения для оценки стоимости исследовательской работы. Неудачные предложения занимают место в лимите и входят в отчёт.

По исчерпании лимита сохранить один итоговый вариант по train-score и закрыть журнал согласно протоколу Arena. Private-финал для пилота не нужен. Результаты пилота используются для планирования ресурсов основной кампании.

## Учёт времени и токенов

Для каждого нового варианта запустить таймер перед первым запросом исследователя по его гипотезе и остановить его при регистрации неизменяемого пакета. Время подготовки включает модельные запросы, работу с кодом, обучение, локальные проверки и повторы. Просуммировать `usage.total_tokens` всех запросов по этому варианту, включая технические повторы, если провайдер вернул usage. При регистрации передать `--seconds` и `--tokens`. Если хотя бы один запрос остался без счётчиков, передать измеренную часть и `--tokens-incomplete`.

Проверку зафиксированного пакета проводить после регистрации через Arena. Записывать её длительность по `elapsed_seconds` между `begin` и `finish`. При повторной технической проверке суммировать длительность всех завершившихся попыток того же кандидата. Токены решателя и метрики равны нулю при подтверждённом немодельном выполнении. Общую оркестрацию и подготовку среды без привязки к кандидату учитывать отдельно.

Для средних по новым вариантам используйте [команду выгрузки](report.md). Отчёт отдельно показывает число наблюдений для каждого среднего. По трём вариантам можно оценить порядок затрат на одну итерацию.

## До запуска

1. Утвердить лимит и закрепить внутренний маршрут DeepSeek V4.1 Flash с доступным usage.
2. По промпту подготовки Arena закрепить версию train, выгрузить обучающую часть и проверочную подвыборку по списку ID, заморозить `ar12-tpr-v3` и проверить runner для трёх стартовых решений и запись затрат на синтетическом прогоне.
3. Сохранить свидетельства в `preparation.md`, затем отдельно запустить поиск по `arena/prompts/start.md`.

Справка о модели — [официальный анонс DeepSeek V4.1 Flash](https://www.deepseek.com/en/news/deepseek-v4-1-flash/).
